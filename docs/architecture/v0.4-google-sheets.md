# Architecture: v0.4.0 — Google Sheets Generator

**Status:** Historical  
**Release tag:** `v0.4.0`  
**Commit:** `33ff603`  
**Architecture style:** Batch processing / single Python application  
**Primary data source:** Google Sheets, with local CSV fallback

## 1. Purpose

OKC Metal Weekly generates Instagram carousel images highlighting upcoming heavy music shows in Oklahoma City and new music releases.

Version 0.4.0 used a Python application to retrieve curated data, transform it into presentation-ready records, and render images.

The architecture prioritized simplicity, low operating costs, manual editorial control, and ease of execution.

## 2. System architecture

```text
Google Sheets                Local CSV
  Shows                        shows.csv
  Releases                     releases.csv
       |                           |
       +-------------+-------------+
                     |
                generate.py
                     |
          Date and include filtering
                     |
           Data preparation and grouping
                     |
           Jinja2 HTML templates
                     |
            Playwright / Chromium
                     |
             PNG + HTML output
                     |
             Instagram publishing
                 (manual)
```

The application was executed locally or through a manually triggered GitHub Actions workflow.

## 3. Data ingestion

### Google Sheets

The application authenticated using a Google Cloud service account and the `gspread` library.

The service account used read-only Google Sheets and Google Drive OAuth scopes.

Two worksheets supplied the data:

**Shows**
- `date`
- `venue`
- `bands`
- `include`

**Releases**
- `release_date`
- `artist`
- `title`
- `type`
- `include`

The application loaded worksheet records into pandas DataFrames.

Show lineups were represented as pipe-separated artist names in a single cell.

### Local CSV fallback

When Google Sheets credentials and spreadsheet ID were not both supplied, the application loaded:

- `data/shows.csv`
- `data/releases.csv`

Both ingestion paths produced DataFrames consumed by the same downstream processing functions.

## 4. Data transformation

The generator performed the following transformations:

1. Resolve the edition start and end dates.
2. Parse dates and discard invalid date values.
3. Filter records to the edition date range.
4. Apply the optional `include` filter.
5. Sort and group shows by date and venue.
6. Split pipe-separated band names into individual names.
7. Group music releases into Albums/EPs and Singles.
8. Calculate presentation font sizes based on content density.

The publication window was configurable in `config.yaml`.

At the tagged v0.4.0 commit, the configuration specified Friday as the starting weekday and an 11-day window.

## 5. Presentation and rendering

The generator used:

- Jinja2 for HTML templating
- `templates/slide.html` for slide layout
- YAML configuration for styling and layout
- Playwright with Chromium for rendering
- A 1080 × 1350 pixel canvas

The default output consisted of four slides:

1. Upcoming live shows
2. Albums and EPs
3. Singles
4. Support local music

HTML and PNG files were written to a date-specific directory under `output/`.

## 6. Configuration

`config.yaml` controlled:

- Publication date calculations
- Canvas dimensions
- Color palettes
- Typography and font fallbacks
- Background image processing
- Film grain, static, and vignette effects
- Layout sizing

This separated visual configuration from application logic, although configuration validation was limited.

## 7. Execution and deployment

### Local execution

The generator could be executed using Python directly or through `generate-week.ps1`.

### GitHub Actions

The `.github/workflows/generate.yml` workflow supported manual execution with a specified edition start date.

The workflow:

1. Checked out the repository.
2. Installed Python dependencies.
3. Installed Chromium.
4. Created a temporary service-account credentials file from a GitHub secret.
5. Executed the generator.
6. Uploaded the generated output as a GitHub Actions artifact.

The workflow used `GOOGLE_SERVICE_ACCOUNT` and `GOOGLE_SHEET_ID` secrets.

## 8. Architectural limitations

### Data integrity

Google Sheets did not enforce relational constraints or unique identifiers for artists, venues, and events.

### Data provenance

Records did not consistently retain their original source URLs or extraction history.

### Change tracking

Edits to spreadsheet records were not captured in a dedicated application-level audit log.

### Reliability

There was no comprehensive automated test suite, ingestion-run tracking, or structured data-quality reporting.

### Coupling

Ingestion, transformation, and rendering logic were implemented within the same Python module.

### Publication reproducibility

The system did not persist a complete record of the exact source data used for each generated edition.

## 9. Future direction

The planned v1.0.0 architecture will introduce PostgreSQL as the system of record, structured ingestion, validation, relational modeling, and publication history.

The migration will preserve the existing rendering capabilities while separating ingestion, transformation, editorial review, and publication into clearer components.
